## F36 — TOCTOU race in GitHub-OAuth first-admin bootstrap (High, 85%)

**File:** `MemorySmith.App/Hosting/GitHubOAuthCallbackHandler.cs`, `OnCreatingTicketAsync` — flagged by lizard as the 4th-most-complex method in the codebase (149 NLOC, CCN 33), which is what prompted a full read.

**The sequence, for a brand-new user with no existing provider link** (lines 107-148):
1. External HTTP call to GitHub's user-info endpoint (line 34, already happened earlier in the method) — network I/O.
2. `db.Users.CreateAsync(...)` — new user record written (line 111-121).
3. `db.ProviderLinks.LinkAsync(...)` — provider link written (line 122-131).
4. `var isFirstAdmin = !await db.Users.HasAnyAdminAsync(ct);` (line 132) — **the check**.
5. `BootstrapGate.Authorize(...)` — the authorization gate TSK-0289 correctly added (loopback/token check).
6. `await db.Roles.AssignRoleAsync(internalUserId, assignedRole, null, ct);` (line 147) — **the act**, potentially minutes... no, realistically milliseconds-to-seconds, but definitely non-zero time, after step 4.

**The gap:** steps 4 and 6 are not wrapped in a transaction, lock, or any atomic "claim first-admin" primitive — they're a plain check-then-act pattern with substantial awaited work in between (steps 1-3 for *this* request, plus whatever concurrent work another simultaneous request is doing). If two people complete the GitHub OAuth flow within the same narrow window during a fresh deployment's initial setup — plausibly the deploying engineer opening the app in two tabs, or two team members racing to claim admin on a freshly stood-up instance — **both requests can observe `HasAnyAdminAsync() == false` before either has committed a role assignment**, and (assuming both satisfy `BootstrapGate.Authorize`, e.g. both are on loopback, or the gate is disabled) both would be assigned `Admin`. This isn't necessarily catastrophic (two admins instead of one isn't itself a compromise), but it's a real violation of the "first admin" invariant the code and its own comments (`// Apply the same bootstrap gate as CreateFirstAdminAsync`) clearly intend to enforce exactly-once, and in the inverse case — one of the two racing requests being the *legitimate* deploying engineer and the other being an opportunistic concurrent request from anyone else who happens to be on loopback at setup time — the outcome is worse than "extra admin," it's "wrong party wins the race."

**Why this wasn't caught by TSK-0289:** that task's evidence trail and acceptance criterion ("first OAuth login from non-loopback with no token → `AuthenticatedDefaultRole`, not Admin") is entirely about *authorization* (should this specific request be allowed to become admin at all) — a single-request, sequential-reasoning question. The race condition is an orthogonal *concurrency* question (given two requests that are each individually authorized to become first-admin, does exactly one of them win) that a single-request-focused fix and test wouldn't surface. This is worth noting as a general pattern for future audits of this codebase: fixing an authorization gap and fixing a concurrency gap in the same code region are genuinely separate verification tasks, and closing one doesn't imply the other was checked.

**Recommendation:** make the first-admin claim atomic. The cleanest fix given this project's SQLite backing: wrap the check-and-assign in a single transaction with `BEGIN IMMEDIATE` (SQLite's write-lock-acquiring transaction mode), or — simpler and more robust against the multi-step nature of this specific method — add a unique constraint / sentinel row approach: an atomic `INSERT OR IGNORE INTO BootstrapClaims (Key, ClaimedByUserId) VALUES ('first_admin', @userId)` (or equivalent CAS-style operation against a dedicated single-row table) *before* doing any of the role-assignment work, and only proceed with `Admin` role assignment if this specific request's insert actually succeeded (i.e., if the row didn't already exist). This turns the race into a database-enforced single-winner outcome instead of an application-level check-then-act.
**Effort estimate:** 4-6 hours including a genuine concurrency test — two simulated simultaneous `OnCreatingTicketAsync` calls (or two calls to whatever the atomic claim primitive becomes) against a fresh in-memory/temp SQLite instance, asserting exactly one succeeds. This is the kind of bug that's easy to "fix" without actually proving the fix closes the window, so the test matters more than usual here.
**Confidence note (85%, not higher):** I traced this by reading the code and reasoning about the await points, consistent with the rigor applied to F17's control-flow trace earlier in this engagement, but I did not (and could not, given this sandbox can't build/run the app) empirically reproduce the race with two actual concurrent requests. Treat this as a well-evidenced logical gap, not an observed incident.

## F35 — `ChatToolCatalog.BuildTools`: cyclomatic complexity 116 (Medium, 90%)

**File:** `MemorySmith.App/Services/ChatToolCatalog.cs`, line 138, `BuildTools()` — lizard: **841 NLOC, 116 CCN, 5290 tokens**, by a wide margin the single most complex method in the codebase (the next-highest, `MemoryChatAgent.ToolLoop.RunToolLoopAsync`, is CCN 52 — less than half). For context, lizard's own default warning threshold is CCN 15; this method is nearly 8x that.

Some of this is inherent to the method's job — it's a single `yield return`-chain enumerating all ~24 `ChatToolDescriptor` registrations (already read in full across the two prior `ChatToolCatalog.cs`-focused reports), and a long flat sequence of independent object constructions isn't the same *kind* of risk as a deeply nested conditional maze (lizard's CCN counts each `yield return`'s surrounding conditionals/switch arms, and with 24 tools each potentially gated by feature flags or environment checks, the count adds up mechanically rather than reflecting genuinely tangled logic). That said, 116 is still worth acting on for a concrete reason: **a single 841-line method is a single unit of code review, a single diff-conflict surface, and a single place where an accidental edit to tool #14 can't be reviewed or tested in isolation from tool #1**. Every finding from the two prior `ChatToolCatalog.cs` reports (F29's unclamped `limit`, the extension-allowlist duplication) lived inside this one method.

**Recommendation:** split `BuildTools()` into category-scoped private methods that each `yield return` a subset, composed via `IEnumerable<ChatToolDescriptor> BuildTools() => BuildSearchTools().Concat(BuildMemoryTools()).Concat(BuildTaskTools()).Concat(BuildPageTools()).Concat(BuildAdminTools());` (or similar groupings matching the tool-name prefixes already visible in the catalog: `memorysmith_search`/`_hybrid_search`/`_context_pack`/`_get` → search; `_memory_create`/`_memory_update` → memory; `_task_*` → task; `_page_*` → page; `_code_search*` → code search). This is a pure structural refactor — each extracted method's `yield return`s are unchanged, just regrouped — and should reduce the single-method CCN from 116 to roughly 15-25 per category method, each independently reviewable. **Effort:** half a day, zero behavior risk if done as a mechanical extraction (the existing `ToDictionary` collision-detection at catalog-construction time, noted as good defensive design in an earlier report, would immediately catch any accidental tool dropped during the split).

## F37 — Audit-logging methods have same-typed positional parameters with no ordering safety net (Medium, 75%)

**File:** `MemorySmith.App/Services/SecurityServices.cs`, `RecordAsync` (line 875, 10 params) and `RecordWithActorAsync` (line 908, 12 params):
```csharp
public async Task<AuditLogEntry> RecordAsync(
    string action, string targetKind, string? targetId, string outcome,
    string? beforeHash = null, string? afterHash = null, string? diffRef = null,
    string? reason = null, object? details = null, CancellationToken cancellationToken = default)
```
Four required `string` parameters back-to-back, then four more optional `string?` parameters — nothing in the type system distinguishes `action` from `outcome`, or `beforeHash` from `afterHash`. Grepped real call sites (10+ found across `AdminController.cs`, `SourceLinksController.cs`, `MemoryApplicationService.cs`, `MaintenanceAgentServices.cs`, `AdminSettingsService.cs`, `ChatModelProfileService.cs`) — **every one calls this positionally**, e.g. `_audit.RecordAsync("role.assigned", "User", userId, MemorySmithAuditOutcomes.Success, details: new { roleName }, cancellationToken: cancellationToken)`. No call site was found using named arguments for the string parameters, which is the one thing that would make a future accidental reorder compiler-safe.

**Why this is worth flagging even with no confirmed live instance of a swap:** this is the exact method responsible for writing this system's audit trail — the record other tooling and, per this engagement's own findings (F36 above, and TSK-0289's evidence trail), *incident review* would lean on. A future engineer adding a new call site, or refactoring an existing one, copy-pasting a similar call and adjusting a couple of arguments, has a real (if not enormous) chance of transposing two same-typed values with zero compiler feedback and zero runtime error — the audit entry would simply be silently wrong, discoverable only by a human noticing the recorded `outcome`/`targetKind`/hash values don't make sense for that entry.

**Recommendation, in order of intrusiveness:** (a) cheapest — add a `// NOTE:` comment at the method declaration flagging the ordering risk and recommending named arguments at call sites, plus a quick pass converting the highest-risk existing call sites (anywhere `beforeHash`/`afterHash` are both passed, since those are the most semantically swappable pair) to named arguments; (b) more thorough — introduce small wrapper types for the parameters most likely to be confused for each other specifically (e.g. a `ContentHashPair(string Before, string After)` struct instead of two loose `string?` parameters), which both documents intent and makes a swap a compile-time-checked non-issue for that pair; (c) most thorough (probably not worth it here) — a builder/fluent API for audit entries. **Recommend (a) now, consider (b) opportunistically** the next time this method is touched for an unrelated reason, rather than a dedicated refactor pass — the risk is real but low-probability-per-edit, and (b)'s full type-safety benefit only matters for the specific pairs most likely to be confused (`beforeHash`/`afterHash` primarily; `action`/`outcome` are usually different-enough string shapes in practice — `"role.assigned"` vs. a constant from `MemorySmithAuditOutcomes` — that a swap there would likely look obviously wrong even without type help).
**Effort:** 1 hour for (a); half a day for (b) if pursued.
