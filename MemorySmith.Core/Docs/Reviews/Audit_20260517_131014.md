## Executive Summary

MemorySmith is in a healthy local-first state. The active solution is now cleanly centered on `MemorySmith.App`, `MemorySmith.Core`, `MemorySmith.Storage`, `MemorySmith.Tests`, and `MemorySmith.Benchmarks`; the old Worker and Dashboard projects are no longer tracked by Git and only appear as ignored local residue. The single-host architecture is the right shape for the product at this stage.

The strongest capabilities are the unified Blazor/API/MCP app, file-backed live wiki, bounded MCP tools, source-link bundles, markdown pages, provider-based chat, streaming chat responses, image/text attachment handling, and optional ONNX semantic ranking with fallback. Validation is strong: Release build passed, docs-site generation passed, the full NUnit suite passed with 148 tests, and workspace diagnostics were clean.

The biggest risks are now security and scale rather than basic functionality. The system needs a central deployment-root file policy before broad agent write capabilities grow further. Today, most write paths are individually constrained to their configured roots, but there is no shared rule that says durable writes must stay under the deployed `Data` directory by default. Agent mode also allows model-proposed memory/page writes automatically when `Chat:AgentWritesEnabled` is true, which is too much trust for a system that will ingest arbitrary knowledge and run chat workflows over it.

Post-audit follow-up on branch `fix/high-roi-hardening-20260517`: this branch makes agent writes opt-in by default, sanitizes generated static wiki HTML, adds a static-site CSP, and corrects the `memorysmith_get` usage-count documentation mismatch. The remaining recommendations still stand, especially deployment-root write policy and human approval/diff workflow for agent writes.

Massive knowledge bases are the next architectural inflection point. Current retrieval is excellent for the 39-record project wiki, but search, stats, context packs, page search, and ONNX ranking still rely on full-store scans or per-query document embedding. That will not hold for tens of thousands of records, multi-page corpora, or long-running chat workflows without a metadata index, durable embedding cache, chunk model, and token-budget-aware retrieval pipeline.

## Priority Findings

### P0 - Add A Central Deployment-Root File Write Policy

Current behavior: durable writes are individually scoped to configured paths, but no central policy proves those configured paths are inside the deployed `Data` folder. Memory writes use `MemorySmith:DataPath`; page writes use `MemorySmith:PagesPath`; event writes use `EventLogPath`; variable writes use `VarsPath`; page assets write under `Pages/assets`; chat image attachments write to OS temp; docs publishing writes `docs/output/wiki`.

Evidence:

- `MemorySmith.App/Program.cs` wires separate configurable paths for data, pages, vars, events, and assets.
- `MemorySmith.Storage/FileMemoryStore.cs` writes wherever its `basePath` points.
- `MemorySmith.Storage/FileVarStore.cs` writes wherever its configured file path points.
- `MemorySmith.Storage/FileEventStore.cs` appends wherever `EventLogPath` points.
- `MemorySmith.App/Services/PageService.cs` keeps page writes under `PagesPath`, but `PagesPath` itself can be outside the deployment folder.
- `MemorySmith.App/Services/ChatServices.cs` stores image attachments under `Path.GetTempPath()/MemorySmith/ChatAttachments`, outside the deployment directory.

Risk: if an operator or future agent-facing configuration points one writable path outside the deployment root, MemorySmith can write durable files outside the intended data boundary. The current path-local checks do not express the user's desired default: block edits outside the deployment directory, with a possible explicit override later.

Recommended fix:

1. Add a canonical deployment root concept, probably `MemorySmith:DeploymentRoot`, defaulting to the parent data folder that contains `Memories`, `Events`, `Graph`, `Models`, and `Pages`.
2. Add `MemorySmith:FileSystem` policy:

```json
{
  "FileSystem": {
    "AllowExternalWrites": false,
    "AllowedWriteRoots": [],
    "AllowExternalReads": false,
    "AllowedReadRoots": []
  }
}
```

3. Introduce a shared `IFileSystemBoundary` or `DeploymentPathPolicy` service that canonicalizes paths and checks every writable root at startup.
4. Fail startup if `DataPath`, `PagesPath`, `EventLogPath`, `VarsPath`, or page asset path resolves outside deployment root while `AllowExternalWrites=false`.
5. Move chat attachment storage under `Data/Temp/ChatAttachments` by default, or add an explicit exception for OS temp with cleanup and restrictive ACLs.
6. Add tests for relative paths, absolute paths, `..` traversal, symlink/reparse escapes, case-sensitive path behavior, and explicit override behavior.

Confidence: 0.92. Priority: P0 because it is the root safeguard for agent-write expansion.

### P0 - Agent Writes Are Automatic When Enabled

Audit-time behavior: `Chat:AgentWritesEnabled` defaulted to true. In Agent mode, `MemoryChatAgent.TryApplyAgentActionsAsync` parses provider JSON and directly writes `memoryWrites` and `pageWrites` through `MemoryApplicationService` and `IPageService`. This branch changes the default to false, but an approval/diff workflow is still needed before broader agent-write use.

Risk: provider hallucination or prompt injection can create or update durable project wiki records and pages without a preview, diff, human confirmation, or rollback workflow. Tool-call execution is read-only, which is good, but Agent-mode structured output is a write path.

Recommended fix:

1. Keep `Chat:AgentWritesEnabled` false by default until an approval flow exists.
2. Add a proposed-write response shape: reply plus pending memory/page changes.
3. Show a diff/preview in `/chat` with Accept, Reject, and Edit controls.
4. Persist approved writes only after explicit user action.
5. Include approval metadata in audit events: actor, source chat, provider/model, original prompt, target IDs/slugs.
6. Add tests proving prompt text cannot bypass approval.

Confidence: 0.90. Priority: P0.

### P1 - Static GitHub Pages Publishing Bypasses The App's Safe Markdown Renderer

Audit-time behavior: `FilePageService.RenderHtml` disables raw HTML by default for the live app, but `docs/build_pages_site.py` used Python `markdown.markdown(...)` directly. Python Markdown allows raw HTML by default, so a script or unsafe HTML in `Data/Pages` could become public static Pages content even if the app rendering blocks it. This branch adds generated-HTML sanitization and a restrictive CSP; a CI fixture should still lock that behavior down.

Risk: `Data/Pages` is intentionally user/agent-editable project wiki content. Publishing it with unsanitized raw HTML creates an XSS risk for the static site and a trust-boundary mismatch between local app rendering and GitHub Pages rendering.

Recommended fix:

1. Keep static output sanitization in `docs/build_pages_site.py` before writing static output.
2. Prefer a single rendering policy shared in concept with the app: raw HTML disabled by default, optional trusted allowlist for media tags.
3. Keep the restrictive Content Security Policy in generated HTML.
4. Add a test or CI check with a malicious page fixture that confirms script tags do not survive static rendering.

Confidence: 0.89. Priority: P1.

### P1 - Remote API Mode Should Require An API Key By Default

Current behavior: when `AllowRemoteApi=true` and `ApiKey` is empty, `OperationalDiagnosticsService` reports a high warning, but startup still succeeds and the API is unauthenticated for remote callers.

Risk: a user enabling remote API for convenience can accidentally expose memory CRUD, pages, chat, MCP, diagnostics, variables, and source-link operations without authentication.

Recommended fix:

1. Fail startup if `AllowRemoteApi=true` and no API key is configured.
2. If unauthenticated remote access is ever desired, require a scary explicit flag such as `AllowUnauthenticatedRemoteApi=true`.
3. Add a health warning and startup log for remote mode even when the API key is present.

Confidence: 0.86. Priority: P1.

### P1 - Massive-KB Retrieval Is Not Yet Indexed Enough

Current behavior: `MemoryApplicationService` calls `_store.LoadAll()` for list filters, lexical search, semantic search, hybrid search, context packs, stats, activity, and source lookup. Page search enumerates markdown files. ONNX semantic search embeds every candidate document during each query.

Risk: this is fine for 39 records, but it will degrade sharply for thousands or millions of knowledge items. Chat magnifies this because every message can run hybrid search, page search, and follow-up tool calls.

Recommended architecture:

1. Add a generated metadata index under `Data/Graph` or `Data/Indexes` containing ID, title, status, tags, references, conflicts, timestamps, usage count, source-link metadata, and page metadata.
2. Add chunk-level indexing for both memories and pages. Treat records/pages as corpus documents with stable chunk IDs.
3. Keep file-backed JSON/markdown as the source of truth, but make search read from indexes.
4. Add a durable embedding cache keyed by content hash, model ID, prefix, and tokenizer settings.
5. Batch embedding updates in maintenance tasks and invalidate incrementally on create/update/delete/page save.
6. Add hybrid retrieval stages: lexical candidate generation, vector candidate generation, recency/usage priors, optional reranking, citation assembly, token-budget packing.
7. Add search latency and index freshness telemetry to `/health`.

Confidence: 0.95. Priority: P1 for the next capability phase; P0 if massive KB support is a near-term goal.

### P1 - Source Bundle Reads Materialize Whole Files Before Truncation

Current behavior: `VarResolver.ReadSourceAsync` uses `File.ReadAllLinesAsync(fullPath)` and then truncates the joined content if it exceeds the configured max.

Risk: `MaxReadBytes` protects output size, not input I/O. A large allowed file can still be fully loaded into memory. This matters for source bundles over large repos and for agent-triggered MCP source reads.

Recommended fix:

1. Read bounded byte ranges or stream line-by-line until the byte budget is reached.
2. Enforce bytes, not characters, matching the option name.
3. Add tests with large files and multi-byte UTF-8 boundaries.
4. Return explicit truncation metadata in JSON output.

Confidence: 0.88. Priority: P1.

### P1 - Chat/MCP Tool Execution Is Duplicated

Current behavior: `McpController` and `MemoryChatAgent` both parse tool arguments and format search/context/get results. Output details already differ between the two paths.

Risk: built-in chat and external MCP agents will drift. Fixes to one tool surface may not reach the other. Structured JSON output is also inconsistent: context packs/source bundles can return JSON, while search tools are mostly text.

Recommended fix:

1. Extract a shared `MemorySmithToolService` for tool schema, argument parsing, execution, output projection, and limits.
2. Have MCP and chat call the same executor.
3. Add `format=json` support to lexical, semantic, and hybrid search tools.
4. Keep text output as the default for humans.

Confidence: 0.91. Priority: P1.

### P1 - Path Boundary Checks Use Case-Insensitive Prefix Comparisons Everywhere

Current behavior: `VarResolver.IsUnderRoot` and `FilePageService.IsUnderPath` use `StringComparison.OrdinalIgnoreCase`. That matches Windows but is looser than Linux file-system semantics.

Risk: on a case-sensitive filesystem, a sibling path differing only by case could be treated as under an allowed root. This is not the top risk for the current Windows service deployment, but CI runs on Linux and future deployments may too.

Recommended fix:

1. Centralize path-boundary comparisons in the new file-system policy service.
2. Use `StringComparison.OrdinalIgnoreCase` only on Windows; use `StringComparison.Ordinal` on case-sensitive platforms.
3. Consider resolving final real paths to handle symlink/reparse-point escapes before reads/writes.

Confidence: 0.78. Priority: P1 as part of the deployment-root policy work.

### P2 - Diagnostics Reveal Full Absolute Paths

Current behavior: `/api/diagnostics` and `/health` include full resolved paths for data, pages, event log, vars, source roots, content root, and base directory.

Risk: acceptable for local-only use, but not for remote/shared deployment. If `AllowRemoteApi=true`, path disclosure gives attackers and external agents detailed host layout.

Recommended fix:

1. Keep full paths in local UI when caller is loopback.
2. Redact or basename paths in API responses for remote callers.
3. Add a `Diagnostics:ExposeFullPaths` option defaulting to false when remote API is enabled.

Confidence: 0.84. Priority: P2 unless remote mode becomes common.

### P2 - Chat Attachment Temp Files Need Lifecycle And Permission Policy

Current behavior: image attachments are saved under the OS temp folder and can be referenced later through `LocalPath`. The UI strips base64 for persisted image attachments, so local chat history can store the server temp path.

Risk: temp files can accumulate, permissions are not explicitly restricted, and paths can be exposed in browser storage. Service accounts and multi-user machines need a clearer lifecycle.

Recommended fix:

1. Move attachments under `Data/Temp/ChatAttachments` by default to honor deployment-root policy.
2. Add retention cleanup on startup and scheduled maintenance.
3. Store opaque attachment IDs in browser/session state rather than absolute temp paths.
4. Apply restrictive ACLs where the platform supports them.

Confidence: 0.82. Priority: P2.

### P2 - Destructive UI Actions Are Inconsistent

Current behavior: chat deletion prompts for confirmation, but memory deletion in `MemoryViewer.razor` and page deletion in `Pages.razor` do not show an explicit confirmation. The page editor has unsaved-change navigation protection; the memory editor does not appear to have equivalent navigation protection.

Risk: human users can accidentally delete durable wiki records or pages. This matters more now that `Data/Pages` and `Data/Memories` are the product's live knowledge base.

Recommended fix:

1. Add confirmation dialogs for memory and page deletion.
2. Add undo or soft-delete for at least one session.
3. Add `NavigationLock` or dirty-state protection for memory editing.
4. Add browser E2E tests for delete/cancel/save flows.

Confidence: 0.86. Priority: P2.

### P2 - README Claims `memorysmith_get` Increments Usage, But Code Does Not

Audit-time behavior: README said `UsageCount` was incremented by `memorysmith_get` and usage API calls, and the MCP tool table said `memorysmith_get` increments usage. In code, `McpController.FormatRecordAsync` and `MemoryChatAgent.FormatRecordAsync` call `MemoryApplicationService.GetAsync`, which does not increment usage. The only increment path is `POST /api/memories/{id}/usage` via `IncrementUsageAsync`. This branch updates README to document `memorysmith_get` as read-only.

Risk: documentation and behavior disagree. Also, because MCP tools are described as read-only, incrementing usage inside `memorysmith_get` would make it a write. The likely better behavior is to keep `memorysmith_get` read-only and fix the docs.

Recommended fix:

1. Decide policy: read-only MCP get, or usage-mutating get.
2. Prefer read-only get for agent safety.
3. Keep README and wiki records aligned: usage is incremented by explicit usage API/UI actions only.
4. Add a regression test proving `memorysmith_get` does or does not mutate usage according to the chosen policy.

Confidence: 0.93. Priority: P2.

### P2 - Live Deployment Drift Should Be Easier To Detect

Current observation: the shared `/health` page appears stale compared with the current source. It reports the old ONNX model path behavior and only two markdown pages.

Risk: operators may believe code changes are live when the service is still running old publish artifacts. This is especially easy with Windows Service deployments that lock published DLLs.

Recommended fix:

1. Add Git commit, build timestamp, and publish path to `/health` and `/api/diagnostics`.
2. Add a publish/restart verification command or script.
3. Add a warning when `AppContext.BaseDirectory` is not the repo/publish path the operator expects.

Confidence: 0.88. Priority: P2.

### P2 - Static Pages Workflow Needs Validation And Dependency Pinning

Current behavior: `.github/workflows/docs-pages.yml` installs latest `markdown` and runs `docs/build_pages_site.py`. There is no generated-site test beyond local execution, no dependency pin, and no XSS fixture.

Risk: renderer changes can alter output unexpectedly; unsafe HTML issue can slip into public Pages.

Recommended fix:

1. Pin Python package versions or use a lock file for docs publishing.
2. Add a script test that generated output contains expected pages and rejects unsafe HTML.
3. Run `actionlint` or another workflow validator in CI.

Confidence: 0.78. Priority: P2.

## Massive Knowledge Base Architecture

The current implementation should evolve without abandoning the file-backed source of truth too early. The most pragmatic path is to keep JSON/markdown records as durable user data, then generate indexes under the deployment data folder.

### Phase 1 - Safety And Observability

- Add deployment-root file policy.
- Add agent write approval.
- Add build/commit/publish metadata to diagnostics.
- Add schema and graph validation.
- Add browser E2E smoke coverage.

### Phase 2 - Unified Corpus And Indexes

- Introduce a corpus abstraction that treats memories, pages, and maybe source snippets as documents.
- Chunk pages and long memories into stable chunk IDs.
- Store metadata index under `Data/Graph` or `Data/Indexes`.
- Store lexical/BM25 index separate from source data.
- Store embedding cache keyed by content hash and embedding configuration.
- Add incremental index updates on memory/page writes and maintenance reconciliation.

### Phase 3 - Retrieval Pipeline

- Query planning: determine whether a request needs direct lookup, broad search, comparison, source evidence, or temporal filtering.
- Candidate generation: lexical, semantic vector, tag/status/source filters.
- Fusion: RRF or weighted scoring with recency/usage/confidence priors.
- Reranking: optional cross-encoder or LLM-assisted rerank for small candidate sets.
- Context packing: token-budget-aware assembly with citations and diversity controls.
- Evaluation: MRR, recall@k, citation correctness, and answer-grounding tests.

### Phase 4 - Large-Scale Operations

- Index freshness health checks.
- Background embedding queue with retry/backoff.
- Import/export tools for large folders, archives, and external docs.
- Duplicate detection and content hash dedupe.
- Snapshot/backup/restore commands for `Data`.
- Optional pluggable backing stores only when file-backed plus indexes are insufficient.

Recommended order: do not jump straight to PostgreSQL or distributed services. First add file-backed generated indexes and a clear corpus/chunk abstraction. Move to SQLite, LiteDB, Lucene indexes, or a vector DB only when metrics show the simpler indexed design is insufficient.

Confidence: 0.91.

3. Durable embedding cache with incremental invalidation.
4. Token-budget context packer.
5. Server-side chat session store and export/search.
6. Retrieval traces, citations, and answer-grounding evaluation.

## Assumptions

- MemorySmith remains local-first and trusted-single-operator by default.
- Remote/shared access should be possible later, but only with explicit safeguards.
- `Data/Memories` and `Data/Pages` are valid project wiki content and should be treated as durable product data.
- The file-backed source of truth should remain until indexes and telemetry prove a heavier backing store is needed.
- Agent writes should be treated as untrusted proposals, even when the selected model is local.

## Unknowns And Open Questions

1. What is the expected target KB size for the next milestone: 1K, 50K, 1M, or larger?
2. Should Agent mode ever write automatically, or should all durable writes be approval-only?
3. Should remote API mode be officially supported in the near term?
4. Should chat history become durable server-side project knowledge, private user state, or both?
5. Which embedding providers should be first-class: ONNX only, OpenAI-compatible APIs, GitHub/Copilot embeddings if available, or a generic provider interface?
6. Should pages get metadata/front matter, or should they remain plain markdown with metadata inferred externally?
7. How strict should deployment-root reads be compared with writes? Source links currently allow configured external read roots.

## Final Assessment

MemorySmith has crossed the line from prototype into a credible local knowledge workbench. The architecture is simpler and healthier than the old split-host design, the test suite is broad, and the chat/MCP surface is genuinely useful.

The next step is to make the power safe and scalable. The most important near-term move is a shared deployment-root path policy plus Agent write approval. Once writes are bounded and reviewable, the product can safely add stronger chat and agent capabilities. After that, the main long-term investment should be indexing: a unified corpus, chunking, durable metadata and embedding caches, and token-budget-aware retrieval for massive knowledge bases.

Confidence in this audit: 0.90 overall. Highest confidence: current architecture, test/build state, security boundary findings, and full-scan scaling limits. Lower confidence: exact performance breakpoints for massive KBs, because no large synthetic benchmark was run in this audit.
